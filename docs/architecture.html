Ludo Royale — System Architecture & Flows

Ludo Royale is a multiplayer Ludo (classic and Quick) and Snakes & Ladders game: a Flutter app for Android and iOS, an authoritative Go backend (REST + WebSocket) backed by PostgreSQL and Redis, and a separate Go bot-play service that plays as labelled bots. This page documents what is implemented in the repository today, verified against the code. Anything not implemented or not yet configured is labelled Pending.

High-level system architecture#

Code: backend/internal/server/server.go, backend/internal/server/extensions.go, backend/cmd/server/main.go · Docs: authentication.md, redis-keys.md

The Go backend is the single source of truth. Clients (the Flutter app and bot-play) send intents — roll, move, join, claim — and render only server-confirmed results. Identity providers only prove who a user is; the backend creates the account and issues its own tokens. Backend instances are stateless: live rooms, sessions and timers are in Redis, so any instance can serve any player and room events fan out across instances over Redis pub/sub.

  • Commands: gateway → rooms.Dispatch → engines; every room change is one Redis commit that also publishes the ordered events on ev:room:{roomId}, which every gateway instance pattern-subscribes to.
  • Money: rooms → wallet (entry fees, payouts); progression → wallet (mission rewards, purchases); auth → identity → wallet (account creation with the welcome grant).
  • Progress: rooms emit a MatchRecord to progression (XP, missions, items), which notifies social (recent opponents); rooms use social to send invites and progression to check emote ownership and seat cosmetics.
  • Pushes: notify publishes per-user messages (wallet.updated, progression.updated, social.*) on ev:user:{userId}.

internal/server/server.go wires every component and is used by both cmd/server and the integration tests, so tests exercise the production wiring. internal/server/extensions.go (DefaultExtensions) adds progression, social and analytics: progression is the match Recorder, inventory and player-info provider; social is the invite sender; the analytics tracker is called for human activity only.

Data ownership and approved schema boundaries#

PostgreSQL holds only durable data, in three schemas of one database. Every user_id references wallet.wallets(user_id); progression rows cascade on account deletion.

  • wallet.wallets holds only balances: user_id, coins, diamonds (both CHECK >= 0). No ledger, history or profile columns.
  • identity.auth_identities maps (provider, subject) → user_id; provider ∈ guest, google, facebook, apple, device; PRIMARY KEY (provider, subject) and UNIQUE (user_id, provider). A guest's subject is the SHA-256 of its guest secret. device (migration 004) is the internal device binding used to restore an account after an app update or reinstall: its subject is an HMAC-SHA256 of platform:deviceId keyed from PUBLIC_ID_KEY, never the raw id; it is never listed as a linked provider. No email or provider-profile columns.
  • progression.*: player_progress, mission_progress, mission_claims, match_receipts (idempotency receipts only), inventory, loadout, friendships.
  • There are no match-history, currency-ledger or profile tables anywhere. Display names and avatars are presentation data cached in Redis.

App-issued access and refresh tokens#

ItemStorageBehaviour
Access tokenClient only (flutter_secure_storage)HS256 JWT, 15 min (ACCESS_TOKEN_TTL); claims sub (account), sid (session family), knd, act (actor type). Verified on every request and checked against the live sess:{sid}, so logout, revocation and replacement by a sign-in on another device are immediate.
Refresh tokenClient secure storage; server keeps only SHA-256Opaque, 30 days (REFRESH_TOKEN_TTL), rotated on every POST /auth/refresh; presenting a rotated token revokes the whole family (refresh_reused).
Guest secretClient secure storage; server keeps SHA-256 as the guest identity subject256-bit, returned once by POST /auth/guest when it creates the account; recovers the guest via POST /auth/guest/resume.
Device bindingClient sends the platform device id (Android 8+ ANDROID_ID, iOS keychain UUID); server keeps only an HMAC as the device identity subjectRestores the account after an app update or reinstall on the same device: POST /auth/device/resume, POST /auth/guest {deviceId}, PUT/DELETE /account/device.
Bot tokensbot-play memory onlyController JWT (15 min) and per-bot session JWTs scoped to one room or the load-test pool (≤ 2 h).

One active device per account (last sign-in wins). Every human sign-in (guest, guest resume, device resume, Google/Facebook/Apple) atomically points usess:{userId} at the new session and deletes the previous one, leaving a sessrep:{oldSid} tombstone. The old device then gets 401 session_replaced from refresh, REST and the WebSocket upgrade, and its live WebSocket is closed at once with 4401 via a {"ctl":"revoke","sid":…} control message on ev:user:{userId} (never forwarded to clients). Bot sessions are exempt. Logout (bearer access token, or the current refresh token when the access token has expired) never writes a tombstone. Long-lived WebSockets also re-check their session every 60 s and close with 4401 once revoked.

Guest login and Save Progress#

Code: backend/internal/httpapi/handlers_auth.go, backend/internal/identity/identity.go, frontend/lib/features/authentication/application/session_controller.dart, presentation/link_account_screen.dart · Status: Implemented

A guest is a real backend account with a wallet — never a Firebase anonymous user and never a locally generated id. Save Progress links a provider identity to the current account id; nothing is ever merged between accounts.

Link outcomeResponseEffect
Identity unused200 {user, wallet}Same account id and wallet; user.isGuest=false; no welcome grant
Already linked to this account200Idempotent
Belongs to another account409 identity_conflict (details.provider)Nothing merged or moved; app offers “Sign in to that account instead” or “Cancel”
Account already has another identity of that provider409 provider_already_linkedNo change

Linking is rate limited to 10 per minute per account. After linking, signing in with that provider on any device resolves to the same account id and wallet.

Restore after update or reinstall (device binding)#

Secure storage does not reliably survive an uninstall, so the account is also bound to a platform device id: Android 8+ sends Settings.Secure.ANDROID_ID (per app-signing key; survives updates and reinstalls, changes on factory reset or a different signing key; Android < 8 sends nothing), iOS sends a random UUID kept in the keychain (survives updates and reinstalls on the same device). The server stores only hex(HMAC-SHA256(k, platform:deviceId)) with k = HMAC-SHA256(PUBLIC_ID_KEY, "ludo-royale/device-id/v1") as an identity.auth_identities row with the internal provider device: one account per device, one device per account. The identifier is used only for this restore.

RequestOutcome
POST /auth/device/resume {deviceId}200 sign-in to the bound account (guest or linked); 404 not_found if unbound; never creates an account
POST /auth/guest {deviceId}200 sign-in to the bound account (no second welcome grant, no guestSecret); else 201 new guest + binding in one transaction
PUT /account/device {deviceId}200 {}: binds to the caller (idempotent; replaces the caller's previous device); 409 identity_conflict if bound to another account (never moved)
DELETE /account/device204, idempotent: "forget this guest"

The binding never appears in linkedProviders and does not make an account "linked": a guest with a device binding still has isGuest = true and is offered Save Progress. Device sign-ins replace the account's previous session like every other sign-in. See authentication.md.

Wallet provisioning, entry fees and payouts#

Code: backend/internal/identity/identity.go, backend/internal/wallet/wallet.go, backend/internal/rooms/game.go (startGame, refund), backend/internal/rooms/scheduler.go (handlePayout) · Status: Implemented

Coins and diamonds are virtual and non-redeemable; there is no real-money wagering. Balances live only in wallet.wallets, which can never go negative.

Exactly-once welcome grant#

Concurrent first sign-ins for the same identity serialize on the (provider, subject) primary key: exactly one transaction commits. This is verified by backend/tests/auth_test.go: TestConcurrentFirstLoginProvisionsOnce (20 concurrent requests → one identity row, one wallet). Amounts come from WELCOME_COINS / WELCOME_DIAMONDS (defaults 1,000,000 and 50).

Entry fees: all-or-nothing debit, refund on a start race#

Fees: ENTRY_FEE_LUDO (default 1,000 coins) and ENTRY_FEE_SNAKES (default 500). Funds are pre-checked when a player joins or creates a room; the authoritative check is the debit at start.

Payout: at most once via a Redis settlement key#

Wallet settlement guarantees#

Referenced from game-rules.md (“Coins”). Every wallet change is a single PostgreSQL transaction, so no partial update can exist. What is not transactional is the boundary between PostgreSQL and the Redis room state; these windows are documented honestly:

OperationGuaranteeMechanismKnown failure window
Welcome grantExactly once per accountWallet + identity in one transaction; (provider, subject) PKNone known
Entry feesAll players charged or none; at most once per room roundDebitAll in one transaction; settle:fee:{room}:{round} guard; refund on start raceIf the process dies after the debit commits but before the room switches to playing, the in-process refund does not run and is not retried; the guard key (24 h) prevents a second charge. A failed refund credit is logged and counted in wallet_settlement_failures_total{op="refund"} but not retried. Neither case is repaired automatically (there is no ledger by design).
PayoutAt most once (never twice)settle:pay:{room}:{round} claimed with SETNX before the credit; failed credits release the claim and retry (≤ 10)A crash between the claim and the PostgreSQL commit loses that payout (no retry).
Mission claims, purchasesExactly onceClaim/inventory row and wallet change in the same transaction (PK)None known (see §13)
Maintenance transitionsNo settlement during maintenanceTimers pushed forward; no auto-moves, forfeits, payouts or debits—

Rooms with a bot seat, practice rooms and load-test rooms are played with entry fee 0 and no coin payout. Bots have no wallet.

Online multiplayer Ludo#

Code: backend/internal/rooms/{lobby,game,commands,store,service}.go, backend/internal/game/ludo, backend/internal/websocket, frontend/lib/core/{realtime,protocol} · Docs: websocket-protocol.md, game-rules.md · Status: Implemented — Flutter play screens implemented and tested (widget tests + live-backend contract test)

Every command passes the same pipeline: per-connection token bucket (WS_MSG_RATE 10/s, burst 20), live version/maintenance check, Redis de-duplication of the client message id (2 min), then rooms.Dispatch. State changes are committed by one Lua script that checks the room revision (optimistic compare-and-set), applies guards and side operations, writes the state with its TTL and PUBLISHes the ordered event batch — so events are published in commit order even with many backend instances.

  • Tokens leave base only on a 6 (Quick Ludo: on a 1 or 6, with 2 tokens per player and both home to win). Exact roll needed to finish; tokens never block; start squares 0/13/26/39 and star squares 8/21/34/47 are safe.
  • Turn deadline TURN_SECONDS (20 s), or TURN_SECONDS_DISCONNECTED (8 s) for a disconnected seat. On timeout the server auto-rolls/auto-moves and adds a strike; MAX_STRIKES (3) consecutive timeouts forfeit the player. Any own action resets strikes.
  • Every turn action carries turnSeq; stale actions are rejected with stale_state and a fresh game.state, which makes double taps harmless.
  • Events carry the new state version v (exactly +1 per event) and h, a 32-bit FNV-1a hash of the canonical position string (test vectors in game-rules.md, checked by backend, Flutter and bot-play tests).
Flutter sidefrontend/lib/app/feature_routes.dart spreads playRoutes (/matchmaking, /practice, /rooms/create, /rooms/join, /rooms/:id/lobby, /game/:roomId) from features/play_routes.dart. The screens build on the realtime core: RealtimeConnection, ActiveRoomController (matchmaking, rooms, roll/move, sync, rematch and chat commands), RoomStateReducer + StateHash, a match event sequencer and turn-input guard in features/game/application, and the Ludo / Snakes & Ladders board renderers, controllers and motion. These screens landed on the documentation date and the frontend team is still finishing them.

Snakes & Ladders flow#

Code: backend/internal/game/snakes_ladders/snakesladders.go, frontend/lib/features/snakes_ladders/presentation/board · Docs: game-rules.md · Status: Implemented (Flutter game screen implemented)

Snakes & Ladders shares rooms, matchmaking, private rooms, timers, fees and the protocol with Ludo. There are no move choices: the server applies the move as part of the roll, so the phase stays awaiting_roll until finished.

  • game.move_applied carries landing (the square reached before a transition, for animation) and transition {kind: snake|ladder, from, to}; the client sets board.positions[seat] = to.
  • Only one transition per move; any number of tokens may share a square; no captures. The board is 10 × 10, numbered boustrophedon from the bottom-left (square 100 at the top-left).
  • State hash canonical string: S|{turnSeq}|{turnSeat}|{positions}.

Private rooms#

Code: backend/internal/rooms/lobby.go (newCode, CreatePrivate, PreviewCode, JoinByCode, StartPrivate, closeRoom), rooms/bots.go, rooms/rematch.go, frontend/lib/features/private_rooms · Status: Implemented — backend; Flutter create, join and lobby screens (features/private_rooms) implemented

Both games use the same private-room machinery. Codes are 6 characters from a 32-symbol alphabet ABCDEFGHJKLMNPQRSTUVWXYZ23456789 (no I, O, 0, 1), drawn with crypto/rand (256 is divisible by 32, so there is no modulo bias), reserved with SETNX roomcode:{CODE} and retried on collision (up to 5 attempts). Input is upper-cased and validated before lookup.

  • Leaving a lobby frees the seat; if the host leaves, host passes to the next seat. When no humans remain the room closes (empty) and its bot sessions are revoked. closeRoom deletes the code mapping (only if it still points to this room), removes the open-lobby entry and clears every player pointer.
  • Leaving during play is a forfeit; leaving after the game counts as declining the rematch.
  • Bots: the host must enable room.allow_bots; seats respect capacity and BOT_MAX_PER_ROOM. Bot seats are labelled bot: true by the server and the game is played with entry fee 0 and no payout.
  • Room TTLs are refreshed on every commit: lobby 30 min, playing 3 h, finished 10 min + rematch window, closed 2 min.

Reconnection#

Code: frontend/lib/core/realtime/{realtime_connection,backoff,active_room_controller}.dart, frontend/lib/core/protocol/room_state_reducer.dart, backend/internal/websocket/{gateway,conn}.go · Status: Implemented (client core and server)

SignalMeaningClient behaviour
1001, 1008, 4400, 4508, heartbeat timeout, abnormal closeShutdown / policy / protocol / slow consumer / dead linkReconnect with full-jitter backoff; snapshot follows
4401Session revoked or expired, or the account signed in on another device (sent immediately)Refresh token, then reconnect; refresh fails → sign-in; refresh fails with session_replaced → “Signed in on another device” popup, sign-in without automatic re-login
4409Replaced by a newer connection of the same session (one live socket per user, across instances)No auto-reconnect; Reconnect button
4426 / 4503Version unsupported / maintenancePolicy re-check → force-update or maintenance screen
4429Rate-limit abuseReconnect after ≥ 10 s
  • Backoff resets after a connection has stayed up for 30 s. Heartbeat: client {"t":"ping"} every 15 s (dead after 10 s without pong); server WebSocket pings every 20 s (closes after a 10 s pong timeout).
  • Commands are idempotent across reconnects: message ids are unique per connection and the server de-duplicates (userId, id) for 2 minutes, answering repeats with ack {dup: true}.
  • Turn deadlines and auto-moves are server-side, so a player who never comes back cannot stall the game (TestTurnTimeoutsForfeitAbsentPlayer, TestReconnectRestoresGame).

Deployment and configuration#

App version management and maintenance#

Code: backend/internal/apppolicy/{policy,store,version}.go, backend/internal/httpapi/router.go (PolicyError), backend/internal/websocket/conn.go (policyBlock), frontend/lib/app/gate/app_gate_controller.dart, frontend/lib/core/app_policy, frontend/lib/features/app_update · Docs: app-version-policy.md · Status: Implemented

The backend decides, per environment and platform, whether a client may use online services. There is no Firebase Remote Config: the policy is a validated JSON file loaded by the backend, so changing it never needs an app release. Modes in precedence order: maintenance → force_update → optional_update → normal (exception: with securityCritical: true, a client below the minimum gets force_update even during maintenance).

Bots (X-App-Platform: bot, accepted only with a bot token) are exempt from the version policy but not from global maintenance. Error details carry the evaluated policy (storeUrl, minimumSupportedVersion, …). Version headers are a compatibility policy, not proof of a genuine binary; authorization and game integrity checks are independent of the gate.

Validation (startup and every reload)

  • environment ∈ development | preproduction | production and equal to APP_ENV (startup fails otherwise)
  • Both android and ios present; versions valid; latest ≥ minimum
  • storeUrl empty, or https://play.google.com/… (Android) / https://apps.apple.com/… (iOS)
  • Windows: endsAtUtc > startsAtUtc; messages ≤ 500 chars; texts may be per-locale maps

Version comparison

  • 1–4 dot-separated non-negative integers: 1.10.0 > 1.9.0, 1.2 == 1.2.0
  • Suffixes such as -beta or +5 are rejected
  • Compared as the tuple (version, build); build matters only when versions are equal; minimum build 0 = any build
  • Invalid or missing client data → 400 client_version_required

Shipped policy files (backend/config/): all three set minimum = latest = 1.0.0 build 1, maintenance off, localized maintenance messages (en, hi, ur, id, ar) and an empty storeUrl — the app therefore shows “update not yet available in the store” Pending store listings. Operator procedures: emergency maintenance = create the flag file (remove it to end); planned = add a window or set enabled, bump configVersion, deploy, kill -HUP; force update = raise the minimum; optional update = raise the latest. There is no HTTP admin API.

Failure behaviour: if the backend is unreachable the app shows “Can't reach the game service” with Retry; the last received policy is cached in SharedPreferences only to show context and never grants access. On the server, an invalid reload never replaces a valid policy.

WebSocket performance#

Code: backend/internal/websocket/{gateway,conn}.go, backend/internal/rooms/store.go (commitScript), backend/internal/metrics/metrics.go, backend/internal/rooms/compression_bench_test.go, frontend/lib/core/realtime/realtime_socket.dart · Docs: performance.md · Status: Implemented

  • Negotiation: the client offers permessage-deflate (RFC 7692) at the handshake; the server runs coder/websocket in WS_COMPRESSION=no_context_takeover by default (disabled and context_takeover are available). connection.ready.compression reports what was negotiated. The application protocol is identical whether or not a frame is compressed.
  • Deltas vs snapshots: gameplay events (game.dice_result, game.move_applied, game.turn_changed, …) are small deltas with v and h; full room snapshots are sent only on join, start, reconnect, game.request_sync, gaps/hash mismatches and queue overflow.
  • Fan-out: each room commit publishes one pre-encoded batch on ev:room:{roomId}; every instance's gateway pattern-subscribes and enqueues to its local members, so players of one room may be on different instances. Per-user pushes (wallet, progression, social, kicks) use ev:user:{userId}.

Progression and engagement#

Code: backend/internal/progression/{record,claim,collection,levels,missions,service}.go, backend/internal/rooms/rematch.go, backend/internal/social, backend/config/{catalog,missions}.json · Docs: progression.md, cosmetics-catalog.md · Status: Implemented — backend; Flutter missions, events, collection, friends, leaderboard and level-road screens (features/meta_routes.dart) implemented

Match completion and rematch (consent-based)#

No rematch starts without each participant's explicit acceptance; leaving or disconnecting past the deadline counts as declining.

Game events → mission progress and XP#

  • Anti-farming: no XP or mission progress for forfeits (left or timed out), fewer than 3 own rolls/moves, or matches shorter than PROGRESSION_MIN_MATCH_DURATION (30 s; ≥ 10 s enforced in production). Bots never earn anything; practice games count for the human within these rules.
  • Missions: 3 daily missions per UTC day chosen deterministically from a pool (sha256(dayKey|missionId)), weekly challenge(s) resetting Monday 00:00 UTC, and time-boxed events (shipped: autumn_cup, 2026-10-19 → 2026-11-02). Period keys dYYYY-MM-DD, wYYYY-Www, e-{eventId}.

nextLevelXp(level) = 100 + 50 × (level − 1); levelXp(L) = 100(L−1) + 25(L−1)(L−2); maximum level 50 (reached at 63,700 XP; XP keeps accumulating for the weekly leaderboard). Milestone items are granted once, server-side, when a level is first reached.

Cosmetic unlock and equip#

Reward verification and wallet updates#

Engagement principles
  • Every item is cosmetic only: nothing changes dice, rules, matchmaking or payouts.
  • No loot boxes or random rewards; purchases are fixed-price and explicit.
  • No punitive streaks: missing a day or week never resets XP, level or collection; only an unclaimed reward of a past period expires.
  • Coins and diamonds are virtual and non-redeemable; no real-money wagering.
  • Bots are visibly labelled and never earn XP; practice and bot rooms charge no fees.

Social (friends by public-id friend code, requests that auto-accept when reciprocal, invites to private rooms for accepted friends only, recent human opponents, weekly friends leaderboard) is implemented in backend/internal/social; online is reported only for accepted friends. Retention: match_receipts 14 days, mission progress/claims 60 days after the period, the rest for the life of the account.

bot-play#

Code: bot-play/internal/{runner,client,connection,config,strategy,ludo,matchmaking}, backend/internal/auth/bots.go, backend/internal/rooms/bots.go · Docs: bot-play.md, bot-play/README.md · Status: Implemented (public fill disabled by default in production config)

bot-play is a separate Go service and a pure protocol client: it uses the same ludo-royale.v1 protocol as the app with server-issued bot tokens. The backend owns dice, legal moves, state, turns, winners and wallets; bots only roll, choose among server-listed legal moves, and leave. bot-play contains no Firebase or analytics SDK.

(a) Relationship between Flutter, the backend, Redis and bot-play#

(b) Bot authentication and room admission#

Bot tokens cannot call wallet, progression, collection, social or account endpoints, cannot create or join rooms by code and cannot chat. The backend enforces a Bot display-name prefix.

(c) Turn-decision lifecycle#

Snakes & Ladders has no choices: bots only roll, and profiles (beginner, balanced, advanced) affect only think time there. A single legal Ludo token is applied by the server, so bots send game.make_move only with two or more.

(d) Runtime configuration reload#

(e) Population reconciliation and scaling#

Hard caps per environment: max_concurrent_bots ≤ 10,000 (development), 5,000 (preprod), 500 (production). The shipped production config serves practice only, with public_matchmaking.enabled: false (backend switch BOT_PUBLIC_FILL_ENABLED defaults to false as well).
