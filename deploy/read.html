3

Deploy

Production is built from GitHub on the VPS. Merge the change into master first, or name a branch, tag or commit for a test deploy.

ludo-deploy deploy                 # master
ludo-deploy deploy ops/vps-deploy  # a branch, tag or commit

What it does

  1. Fetches the repository and resolves the ref to a commit.
  2. Builds backend and bot-play with Go 1.27.3 into /opt/ludo-arena/releases/<utc>-<commit>/, copies backend/config/ and bot-play's production.yaml + profiles.yaml, and checks bot-play's configuration.
  3. If any backend/migrations/*.sql file differs from the live release, takes a database backup first (/var/backups/ludo-arena/*-pre-<release>.dump).
  4. Points current at the new release and restarts the backend (which applies the migrations at startup), then waits up to 30 s for /readyz.
  5. If the health check fails, it switches back to the previous release by itself and exits with an error. The failed build stays on disk.
  6. Restarts bot-play in the background and deletes old releases (keeps 5).

Check the result

ludo-deploy status
curl -s https://ludo.sungamestudio.com/readyz        # {"status":"ready"}, from anywhere
journalctl -u ludo-backend -n 50 --no-pager
What players notice (measured)A deploy takes about 45 s, but players only see the backend restart. On SIGTERM the backend closes every WebSocket (code 1001) and drains in-flight HTTP requests, including bot-play's 20 s assignment long-poll, so the old process exits 10–20 s later and only then does the new one start. During that gap REST calls answer 502 and the app keeps retrying its socket; it reconnects and resyncs once the new process is up. Running games continue because their state is in Redis. bot-play waits for its running practice games to finish (up to 5 minutes) before it restarts. Deploy when traffic is low; a rollback has the same 10–20 s gap.

Only one deploy or rollback runs at a time (lock in /run/ludo-deploy.lock).

Roll back

ludo-deploy list                                # releases, * = live
ludo-deploy rollback                            # the release before the live one
ludo-deploy rollback 20261022150102-1a2b3c4     # a specific one

Rollback re-points current and restarts; it does not rebuild anything.

The database is not rolled backThe backend never undoes a migration, so the older release runs on the newer schema. That works when migrations only add things (5.2). If a migration itself is the problem, fix it forward with a new migration and deploy. As a last resort, restore the backup taken before that deploy (5.4); that loses every wallet, purchase and progression change made since.

If ludo-deploy itself is broken:

ls /opt/ludo-arena/releases
ln -sfn /opt/ludo-arena/releases/<name> /opt/ludo-arena/current
systemctl restart ludo-backend ludo-bot-play
5

Database

5.1 What is stored where

PostgreSQL (ludo_arena) holds accounts, wallets, progression, purchases and reports in the schemas wallet, identity and progression. Live games, matchmaking, sessions and timers live in Redis only. The table list is fixed by the owner (CLAUDE.md, enforced by backend/tests/schema_guard_test.go); ask before adding tables.

sudo -u postgres psql ludo_arena                    # interactive
sudo -u postgres psql ludo_arena -c '\dt wallet.*'
sudo -u postgres psql ludo_arena -c 'SELECT count(*) FROM wallet.wallets WHERE NOT is_bot'   # accounts

Be careful with writes: there is no undo except a backup restore.

5.2 Schema changes (migrations)

  1. Add backend/migrations/NNN_short_name.sql (next number). The backend runs every migration file at every startup, in name order, under an advisory lock, so each file must be idempotent (CREATE TABLE IF NOT EXISTS, ADD COLUMN IF NOT EXISTS, ON CONFLICT DO NOTHING, …).
  2. Keep it backward compatible, so the previous release still works on the new schema and a rollback is safe: add nullable columns or columns with a default, add tables or indexes, never rename or drop in the same release. Drop old things in a later release, once nothing uses them.
  3. Test it locally and in the e2e tests (TEST_DATABASE_URL=… go test ./...), merge, then ludo-deploy deploy. The deploy backs up the database first, and the backend applies the migration when it starts.
  4. Check journalctl -u ludo-backend -n 30 (a failed migration stops startup, and the deploy rolls back by itself), then ludo-deploy status.

Large tables: CREATE INDEX CONCURRENTLY cannot run in a transaction; keep such statements in their own file and test the lock time on a copy first.

5.4 Restore a backup

This replaces the whole database with the dump.

ludo-deploy backup before-restore                  # keep what is there now
systemctl stop ludo-bot-play ludo-backend
sudo -u postgres pg_restore --clean --if-exists --no-owner --role=ludo \
  -d ludo_arena /var/backups/ludo-arena/<file>.dump
systemctl start ludo-backend ludo-bot-play
ludo-deploy status

5.5 Redis

export REDISCLI_AUTH=$(awk '{print $2}' /etc/redis/ludo-arena-secret.conf)
redis-cli info clients | head; redis-cli dbsize
Never flush production RedisRedis holds live games; never run FLUSHALL or FLUSHDB. Data survives restarts (AOF every second + RDB in /var/lib/redis). A Redis restart pauses play for a few seconds; the backend reconnects by itself.
6

Change server configuration

The files in deploy/ are the source of truth for the server. Change them in the repo first, then apply them on the server, so the next provisioning gives the same result.

6.1 Backend settings (/etc/ludo-arena/backend.env)

nano /etc/ludo-arena/backend.env
systemctl restart ludo-backend          # sockets reconnect, like a deploy
  • systemd reads this file: one KEY=value per line, no inline comments, no quotes. Option reference: backend/.env.example.
  • provision.sh creates it once from deploy/backend.env.example and never overwrites it. When a release needs a new setting, add the key to backend.env.example in the repo and to the server's file by hand.
  • Secrets in it: JWT_SIGNING_KEY (changing it signs every player out), PUBLIC_ID_KEY (never change it: it would orphan every device binding and change every public player id), ACTIVE_USER_KEY, the DATABASE_URL password, REDIS_PASSWORD, BOT_SERVICE_KEY_SHA256, the four R2_* (profile pictures and emotes) and GOOGLE_PLAY_SERVICE_ACCOUNT_FILE. Never commit them.

6.2 App policy, entry fees, catalogues, coin packs

These are files in backend/config/ and ship with every release: change them in the repo, merge, ludo-deploy deploy. The app policy (app-policy.production.json: minimum versions, maintenance windows, entry fees, welcome grant) is also re-read every 5 s and on systemctl reload ludo-backend.

Emergency maintenance without a deploy:

touch /etc/ludo-arena/MAINTENANCE     # players see the maintenance message
rm /etc/ludo-arena/MAINTENANCE        # back to normal

6.3 nginx

Edit deploy/nginx/ in the repo, copy the file to the server, then:

nginx -t && systemctl reload nginx

A reload keeps existing WebSockets on the old workers for up to 30 s (worker_shutdown_timeout); after that they are closed and the app reconnects.

6.4 Kernel limits, PostgreSQL, Redis, units, firewall

Edit the files in deploy/, then re-run provisioning. It is idempotent and keeps secrets, data and certificates.

# on the Mac, from the repository root
scp -r deploy root@ludo.sungamestudio.com:/root/
ssh root@ludo.sungamestudio.com bash /root/deploy/scripts/provision.sh
Brief disruptionProvisioning restarts Redis, PostgreSQL and nginx (a few seconds): run it when traffic is low. It does not restart the backend; run systemctl restart ludo-backend if a unit file changed.

6.5 bot-play

Its settings are bot-play/configs/environments/production.yaml in the repo, deployed with each release. public_matchmaking is off: bots join only practice games. To fill public lobbies, turn it on in that file, set BOT_PUBLIC_FILL_ENABLED=true in backend.env, deploy, and restart the backend.

6.6 Operating system

unattended-upgrades installs Ubuntu security updates automatically. All services start on boot, so a reboot (reboot, or Bluehost → Reboot Server) only interrupts play briefly.

7

TLS certificate & DNS

  • The certificate renews itself (systemctl list-timers certbot.timer); a hook reloads nginx afterwards. Test renewal with certbot renew --dry-run. The expiry date is in ludo-deploy status.
  • DNS is in Cloudflare → sungamestudio.com → DNS → Records, not Namecheap. Keep ludo on DNS only. The orange-cloud proxy would put Cloudflare's idle timeouts in front of game sockets, change the client IP the backend sees (TRUSTED_PROXY_HOPS, nginx real_ip) and break the Let's Encrypt HTTP check as configured here.

Rebuild the server from scratch

  1. Reinstall Ubuntu 24.04 (Bluehost → Server Image → Reimage) and point the Cloudflare ludo record at the new IP (DNS only).
  2. From the repository root on a Mac: scp -r deploy root@<ip>:/root/ && ssh root@<ip> bash /root/deploy/scripts/provision.sh
  3. The first run stops after printing a new deploy key. Add it in GitHub → Ludo-Arena → Settings → Deploy keys (read-only; delete the old one) and run provision.sh again.
  4. Add the values that are not generated on the server to /etc/ludo-arena/backend.env: the four R2_*, and GOOGLE_PLAY_SERVICE_ACCOUNT_FILE=/etc/ludo-arena/secrets/google-play.json after copying the key there (chown root:ludo, chmod 0640).
  5. Restore the latest database dump (5.4), then ludo-deploy deploy.
Keep players signed inA new server generates new JWT_SIGNING_KEY and PUBLIC_ID_KEY. To keep players signed in and their device bindings, copy /etc/ludo-arena/backend.env from the old server instead (step 4).
